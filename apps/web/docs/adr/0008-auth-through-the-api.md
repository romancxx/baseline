# 8. Auth through the API

- **Status:** accepted
- **Date:** 2026-11-09
- **Phase:** 8 — Auth through the API

## Context

Signing in, creating an account and signing out move from Supabase Auth to `apps/api` ([api 0005](../../../api/docs/adr/0005-authentication.md)).
The API issues a 15-minute access token and a single-use refresh token in a cookie scoped to `/api/v1/auth`; reusing a refresh token revokes all of the user's tokens.
The API has no CORS and the web app keeps Server Components for reads and server actions for writes, so Next is a backend-for-frontend: the browser talks only to Next, and Next's server calls the API.
Supabase stays for data until the next phase removes it.

## Decision

- **Tokens live in two plain `HttpOnly` cookies on Next's origin**, `sn_access` and `sn_refresh`, both `Path=/` and `SameSite=Lax`, `Secure` when `NEXT_PUBLIC_APP_URL` is https.
  No encryption: a stolen cookie is replayed whether it is sealed or not, and sealing would add a secret to manage.
  `Lax`, not `Strict`, so a link from another site arrives signed in.
- **The access cookie expires 60 seconds before its token.**
  A missing access cookie beside a refresh cookie means "refresh"; Next never decodes the JWT.
  The refresh cookie lives 30 days, like the API's.
- **The API's refresh cookie never reaches the browser.**
  Next reads it from the API's `Set-Cookie` and sends it back in a `Cookie` header, so the API's `SameSite`, `Secure` and `Path` flags do not constrain where either app is deployed; Next only needs to reach the API.
- **Only `proxy.ts` refreshes**, before rendering.
  It writes the new cookies onto the request, so the same request's Server Components and actions read them, and onto the response, so the browser keeps them.
  Server Components cannot set cookies, so a refresh there would rotate the token and lose its replacement.
- **Gating is optimistic.**
  `proxy.ts` decides "signed in" from the cookies, after refreshing if needed; the first API call of the page (`GET /users/me` in the app layout) is the authoritative check.
  Only a 401 from refresh clears the session; a network error or a 5xx lets the request through, so an API outage signs nobody out.
- **A 401 while rendering goes through `GET /session/expired`**, a public route handler that clears the cookies and redirects to `/sign-in`.
  Redirecting straight to `/sign-in` with the cookies still set would loop through `proxy.ts`.
  Server actions clear the cookies themselves.
- **Concurrent refreshes are deduplicated in Next's process.**
  One refresh is in flight per refresh token, keyed by its hash, and its result stays cached for 30 seconds, so prefetches and tabs still carrying the old cookie receive the new tokens instead of reusing the old one.
- **One request ID per incoming request**, assigned by `proxy.ts`, passed as a request header, sent to the API as `X-Request-ID` and logged.
  An ID sent by the browser is ignored.
- **The client is `openapi-fetch` over types generated by `openapi-typescript`** from `apps/api/openapi.json`.
  Both the schema and the generated types are committed; each app's CI regenerates its file and fails on a diff.
  The generated types are the contract for requests and responses, which are not parsed with Zod; `data/` still maps them to camelCase domain objects.
- **Errors are values.**
  The client returns `{ ok: true, data } | { ok: false, error: ApiError }`; reads throw on failure, actions turn the error into a `FormState`.
  The error body is parsed with one Zod schema, because the API's OpenAPI schema does not describe its `{ code, message, details }` errors; a body that does not parse becomes `unexpected_response`.
- **A duplicate email is told apart by its code**, `email_taken`, which the API adds for it.

## Consequences

The deduplication holds only while the web app runs as one long-running Node process.
Two instances refreshing the same token would look like reuse and sign the user out everywhere; the fix then is a grace period in the API (see [improvements.md](../improvements.md)).
A forged link to `/session/expired` can sign someone out of Next without revoking anything at the API.
The API's routes, parameters and bodies are checked by `tsc`, but nothing checks at runtime that the running API matches the committed schema.

## Alternatives considered

Sealed cookies (iron-session, jose): a secret to manage for no protection against replay.
`SameSite=Strict`: signed out on every arrival from another site.
Refreshing in the data-access module: impossible to persist from a Server Component.
A grace period in the API: works across instances, but weakens reuse detection and, with refresh tokens stored only as hashes, cannot return the same new token twice.
Hand-written Zod schemas per response: runtime checks, but drift from the API surfaces only at runtime.
Zod schemas generated from OpenAPI (orval, openapi-zod-client): heavier tooling for the same drift check.

# 5. Home

- **Status:** accepted
- **Date:** 2026-11-13
- **Phase:** 5 — Home

## Context

Home at `/` showed only its heading.
The API now serves, besides the overview, the latest brief of each security held at `GET /portfolio/briefs`: listings of one share class grouped as one security, entries with a brief newest generated first, then the others by name, and ETFs flagged with `news_collected: false` and never a brief.
The overview's totals carry `prices_as_of`, the latest close among the valued holdings.
The design ([screens 02 and 03](../design/screens.html)) opens Home with three tiles, a disclaimer, the latest briefs beside the five largest holdings, and gives it an empty, a server-down, a partial and a loading state; the top bar shows "Prices · close of 5 Nov".

## Decision

- **Home's order is the API's.**
  The brief cards, the "No brief yet" names and the ETF count are three groups split from the API's list, each keeping its order; the briefs tile's "Last generated" is the first entry's brief, the newest.
  The Holdings card lists the first five valued holdings of the overview, which comes largest value first.
  The web app sorts nothing and does no arithmetic on a figure: it counts entries.
- **The brief card is reused**, given an optional security: the card is then headed and named after it, linking to its first held listing's page, and leaves the disclaimer to the page's one line.
- **Home belongs to `news`**, composing the Holdings card, the missing-prices notice and the empty state from `portfolio` through the existing edge.
  The empty state moved out of the Holdings table into `portfolio`, so both screens render the same one.
- **Home streams under one `Suspense` boundary** whose fallback mirrors the loaded page: the tiles with their labels, the disclaimer, a brief card and the Holdings card.
- **The prices as-of stamp returns to the top bar**, on every signed-in page, superseding that line of [ADR 0003](0003-holdings-search-and-instrument-page.md).
  The `(app)` layout renders `PricesAsOf` from `portfolio` under `Suspense`, so the shell does not wait for the overview; the read is `cache()`d, so a page that also reads the overview makes one call.
  Without a valued holding there is no stamp.
- **A failed read shows "Couldn't reach the server" with Try again**, which fetches the segment again from the server through the boundary's `retry`.
  `(app)/error.tsx` shows it inside the shell when a page's read fails; `app/error.tsx` shows it without the shell when the `(app)` layout's own reads fail, the user's or the stamp's.

## Consequences

When the API cannot be reached, the layout's read of the user fails first, so the server-down state shows without the top bar, where the design keeps it.
A failure of the overview alone, on a page that does not read it, now fails that page through the stamp.
The design's "7 of 12 holdings" beside "Latest briefs" is not built.
The skeleton avoids a shift for a portfolio with holdings; an empty portfolio replaces it with the empty state.

## Alternatives considered

Reading the overview in the layout before rendering: every page, and Home's skeleton, would wait for it.
Catching the stamp's failure to keep the shell: a second way of reading the API beside `dataOrThrow`, for a line of the bar.
Sorting the holdings or briefs in the web app: the API documents its order, and sorting decimal strings means turning figures into numbers.
